# transformers>=4.57 / trl>=0.20 required: Qwen3-VL("qwen3_vl") and Qwen3.5
# ("qwen3_5") are only registered in transformers builds >= 4.57.0.dev0, and TRL's
# SFTConfig renamed max_seq_length -> max_length around the same time. Older
# pinned minimums here would silently resolve to versions that can't load
# Qwen3-VL/Qwen3.5 configs at all, or crash on SFTConfig(max_seq_length=...).
#
# PINNED EXACTLY (not >=): unpinned ranges here were observed, on this exact repo, to
# resolve to DIFFERENT transformers/trl releases across separate `pip install` runs
# made only minutes apart (transformers 5.15.0 / trl 1.9.2 in one run, an older release
# without that in another) -- and TrainingArguments.warmup_ratio was REMOVED as an
# __init__ kwarg in one of those releases (consistent with the
# "warmup_ratio is deprecated ... removed in v5.2" warning seen on the older one),
# causing `SFTConfig(warmup_ratio=...)` to raise `TypeError` non-deterministically
# depending purely on job-submission timing. Exact pins make training runs
# reproducible; bump deliberately (and re-verify --debug) rather than letting `pip`
# silently pick up new releases mid-experiment.
#
# `trl` is pinned to a GitHub commit, NOT the latest PyPI release (1.9.2 as of this
# writing), because of a CONFIRMED, SEVERITY-CRITICAL bug in 1.9.2 when paired with
# transformers==5.15.0: `SFTTrainer._prepare_dataset`'s prompt/completion tokenize path
# calls `processing_class.apply_chat_template(example["prompt"], tokenize=True,
# add_generation_prompt=True, ...)` (no `return_dict=True`) and then unwraps the result
# via `prompt_ids[0] if isinstance(prompt_ids[0], list) else prompt_ids` -- a heuristic
# written for an older convention where that call returned a plain `list[int]` (or
# `list[list[int]]` for batched VLM calls). In transformers==5.15.0, that same call
# instead returns a `BatchEncoding` (dict-like, keys "input_ids"/"attention_mask");
# indexing `[0]` on it returns a `tokenizers.Encoding` object, not a `list`, so the
# isinstance check fails and `prompt_ids` is left as the *unwrapped* `BatchEncoding`
# itself. `len(prompt_ids)` then evaluates to 2 (the number of dict KEYS, not tokens),
# so `completion_mask = [0]*len(prompt_ids) + [1]*(...)` masks out only the first 2
# tokens of every single sample instead of the actual (much longer) prompt -- meaning
# loss ends up computed over almost the ENTIRE sequence (system prompt + user question
# included), not just the intended assistant completion. This exact chain was verified
# directly against a real training sample + the real Qwen3.5-9B tokenizer (see chat
# history for the full repro). It also explains the
# "Mismatch between tokenized prompt and the start of tokenized prompt+completion"
# warning logged on literally every sample: comparing 2 sliced ids against a whole
# BatchEncoding object can never be equal, regardless of actual tokenizer behavior.
# TRL's `main` branch has since refactored this into a `_tokenize()` helper
# (`trl/data_utils.py`) that always passes `return_dict=True` and reads `["input_ids"]`
# directly -- sidestepping the fragile shape-based heuristic entirely -- but as of this
# writing that fix has not yet been included in any published PyPI release (`1.9.2` is
# still latest and still has the bug). Pinning to this specific commit (rather than a
# floating `@main`) keeps training runs reproducible; re-verify with --debug (checking
# that no "Mismatch between tokenized prompt" warning appears) before bumping to a
# future PyPI release that includes this fix, and switch back to a plain `trl==X.Y.Z`
# pin once one is available.
